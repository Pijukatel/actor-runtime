# Nightly CRM import pipeline

Four Actors that model a nightly CRM import on the Apify platform, built to run on this
repository's local Actor runtime. They coordinate **only** through named datasets, named
key-value stores and the Actor runs API - there are no request queues anywhere in the pipeline,
and no Actor touches the network: every byte of data is generated by the simulator.

```
import-supervisor
  ├─ export-simulator ──────────► crm-exports (KVS)   region-1..8.csv, expected-report.json
  ├─ region-importer × 8 ───────► crm-normalized (DS) valid, normalized contacts
  │  (max 4 concurrent)           crm-quarantine (DS) { region, rowNumber, reason, raw }
  └─ reconciliation-reporter ───► crm-master (DS)     one row per unique contact
                                  OUTPUT (its own default KVS) the reconciliation report
```

## The Actors

### `export-simulator`

Input `{ seed }`. From a single mulberry32 stream it generates 8 regional exports of 5000 rows
each (`id, name, email, phone, updatedAt, region`) and stores them as CSV in the named key-value
store `crm-exports` under `region-<n>.csv`. The same seed always produces byte-identical exports.

Defects are injected deterministically:

| defect                                         | rate                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------ |
| duplicate contacts across regions              | ~10% of all rows (same person, different formatting, new local id)                         |
| mixed date formats                             | 6 formats: ISO 8601, zone-less, `DD.MM.YYYY`, `DD/MM/YYYY hh:mm`, epoch seconds, date-only |
| unnormalized emails / phones / names           | case, padding, `<addr>` wrapping, `00420`/`+420`/national/`(nnn) nnn-nnn` phone forms      |
| malformed rows (wrong column count)            | 2.0-3.4% per region, **7% for region 7**                                                   |
| unparseable values (id / email / phone / date) | ~1.1% per region combined                                                                  |

It then makes one single-process reference pass over exactly the bytes it just published, using
the same normalization rules the importers use (`src/crm.js`), and saves the result as
`crm-exports/expected-report.json`:
`{ totalRows, imported, quarantinedByReason, duplicatesMerged, uniqueContacts }`.
That file is the ground truth the distributed pipeline is measured against.

### `region-importer`

Input `{ region, force }`. Reads `crm-exports/region-<region>.csv`, parses it (quote-aware,
RFC4180-ish) and normalizes every row: emails lowercased and trimmed, phones reduced to digits
with the `+420` prefix rule (an explicit `+`/`00` prefix keeps its own country code, a bare
9-digit national number gets `+420`), `updatedAt` converted to ISO 8601. Valid rows are appended
to the named dataset `crm-normalized`, invalid ones to `crm-quarantine` as
`{ region, rowNumber, reason, raw }` (`rowNumber` is the 1-based data row, the header excluded).

**Circuit breaker.** The whole file is parsed and classified before anything is written. If more
than 5% of the rows are malformed (wrong column count) and `force` is not `true`, the run logs the
rate and exits with a non-zero code having written nothing at all - region 7 is the export that
trips it.

### `import-supervisor`

The entry point. Input `{ seed, maxConcurrency = 4, maxAttempts = 3 }`.

1. Drops yesterday's `crm-normalized` / `crm-quarantine` / `crm-master` so the run measures itself.
2. Starts `export-simulator` and polls the runs API until it finishes.
3. Runs `region-importer` for regions 1-8, at most 4 in flight, polling every run's status.
4. A region that ends `FAILED` is relaunched with `force=true`, up to 3 attempts per region; the
   failed run's own log is pulled back so the circuit-breaker line appears in the supervisor's log
   too, and every retried region is recorded.
5. Once all 8 regions have `SUCCEEDED`, runs `reconciliation-reporter` and waits for it, loads its
   `OUTPUT` and the simulator's `expected-report.json`, compares them field by field, and ends its
   log with `RECONCILIATION PASS` or the exact per-field diff (in which case the run itself fails).

### `reconciliation-reporter`

Input `{ regionsRetried }`. Reads `crm-normalized`, deduplicates by normalized email keeping the
row with the latest `updatedAt` (ties break on id, then region, so the result never depends on the
order in which the importers happened to append), writes the surviving contacts to the named
dataset `crm-master`, and writes its `OUTPUT`:
`{ totalRows, imported, quarantinedByReason, duplicatesMerged, uniqueContacts, regionsRetried }`.

## Shared code

`shared/crm.js` holds the CSV parsing, normalization and dedup rules - the single definition of
"what a correct pipeline does with a row". Because each Actor is pushed as a self-contained source
folder, it is copied into every Actor that needs it by `./sync-shared.sh`; run that after editing it.

## Running it on the local Actor runtime

```bash
docker build -t actor-runtime .
docker run -d --name actor-runtime -p 3333:3333 -p 3000:3000 \
  -v /var/run/docker.sock:/var/run/docker.sock -v "$(pwd)/data:/data" actor-runtime

export APIFY_CLIENT_BASE_URL=http://localhost:3333
export APIFY_CONSOLE_URL=http://localhost:3000
apify login --token any-non-empty-token

for actor in export-simulator region-importer reconciliation-reporter import-supervisor; do
  (cd crm_pipeline/$actor && apify push)
done

cd crm_pipeline/import-supervisor && apify call --input '{"seed":20240301}'
```

The supervisor needs the other three Actors to exist under their own names, so push all four
before calling it. With seed `20240301` the pipeline produces:

```json
{
	"totalRows": 40000,
	"imported": 38178,
	"quarantinedByReason": {
		"malformed_row": 1357,
		"missing_id": 47,
		"invalid_email": 172,
		"invalid_phone": 113,
		"invalid_date": 133
	},
	"duplicatesMerged": 3685,
	"uniqueContacts": 34493,
	"regionsRetried": [7]
}
```

A full pipeline run takes roughly two minutes on the local runtime. `run-log.md` in this folder is
the log of one such passing run.
